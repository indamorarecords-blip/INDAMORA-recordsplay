INDAMORA PLAY — FINALISATION DE L’EXISTANT

Audit technique + correction minimale + préparation à la production

Tu travailles sur le projet existant INDAMORA PLAY.

Le projet existe déjà et possède une base fonctionnelle, technique et graphique importante.

OBJECTIF PRINCIPAL

NE PAS REFAIRE INDAMORA PLAY.

L’objectif est de finaliser proprement l’existant, avec le minimum absolu de modifications nécessaires.

INDAMORA PLAY doit évoluer progressivement vers une plateforme réunissant :

* musique
* artistes
* créateurs
* professionnels
* médias
* partenaires
* communauté

Le RÉPERTOIRE doit devenir le point central de cet écosystème.

⸻

1. RÈGLE ABSOLUE : PRÉSERVER L’EXISTANT

Avant toute modification :

1. inspecter le code existant ;
2. identifier les fonctionnalités réellement opérationnelles ;
3. identifier les fonctionnalités incomplètes ;
4. identifier les fonctionnalités cassées ;
5. identifier les risques de sécurité ;
6. identifier les données de démonstration ;
7. identifier les dépendances entre les fonctionnalités.

NE PAS :

* refaire le projet ;
* changer l’architecture sans nécessité ;
* remplacer une fonctionnalité fonctionnelle ;
* supprimer une fonctionnalité existante ;
* créer une nouvelle interface simplement parce qu’elle serait différente ;
* multiplier les menus ;
* changer inutilement les composants ;
* modifier inutilement le design ;
* modifier le logo ;
* modifier le domaine ;
* remplacer les parcours utilisateurs existants ;
* supprimer les données existantes sans raison technique indispensable.

RÈGLE :

Si une fonctionnalité fonctionne déjà correctement → NE PAS LA MODIFIER.

Si une fonctionnalité fonctionne partiellement → la finaliser.

Si une fonctionnalité est cassée → la corriger avec la modification minimale nécessaire.

Si une fonctionnalité n’est pas nécessaire à la mise en production → ne pas la créer maintenant.

Le serveur initialise actuellement un catalogue avec des artistes et œuvres de démonstration.

Ces données sont utiles pour le développement et les tests.

Mais elles ne doivent pas être transformées en faux contenu de production.

NE PAS :

* inventer de nouvelles œuvres ;

* créer de faux utilisateurs ;

Ne supprimer les données de démonstration que si cela est nécessaire pour la mise en production.

Le RÉPERTOIRE doit être le cœur de l’écosystème INDAMORA PLAY.

Avant toute nouvelle fonctionnalité, vérifier que le RÉPERTOIRE fonctionne réellement.

4. ARTISTES ET RELATIONS DE DONNÉES

Vérifier la relation entre :

* artistes ;
* œuvres ;
* profils ;
* utilisateurs ;
* médias.

Une faiblesse actuellement identifiée est que certaines œuvres semblent être reliées à l’artiste par une donnée textuelle plutôt que par une véritable relation structurée.

Vérifier avant de modifier.

Si cette architecture provoque réellement :

* des incohérences ;
* des doublons ;
* des problèmes de recherche ;
* des problèmes de filtrage ;
* des problèmes de suppression/modification ;
* des problèmes de permissions ;

alors améliorer progressivement la relation.

Préférer une relation structurée du type :

artist.id → work.artist_id

ou une table relationnelle si plusieurs artistes doivent être associés à une même œuvre.

MAIS :

Ne pas migrer inutilement la base de données si le fonctionnement actuel est déjà fiable.

Toute migration doit être :

* justifiée ;
* rétrocompatible si possible ;
* testée ;
* vérifiée après migration.

5. UPLOADS ET STOCKAGE — PRIORITÉ TECHNIQUE

Vérifier le système actuel d’upload et de stockage.

Le projet utilise un système de stockage objet et des URLs d’upload signées.

Vérifier notamment :

* authentification ;
* autorisation ;
* type MIME ;
* taille maximale ;
* expiration des URLs ;
* ACL ;
* visibilité public/privé ;
* accès aux fichiers ;
* téléchargement ;
* lecture audio ;
* lecture vidéo ;
* suppression ;
* fichiers orphelins.

Problème potentiel identifié

Une URL d’upload peut être créée avant qu’un fichier soit correctement rattaché à une entité métier.

Cela peut provoquer des fichiers orphelins.

Ne pas refaire le système.

Si le problème est confirmé, introduire uniquement le minimum nécessaire pour sécuriser le cycle :

upload demandé → upload effectué → validation → rattachement → publication

Une éventuelle logique de upload session doit notamment pouvoir associer :

* utilisateur ;
* objet ;
* type de contenu ;
* chemin du fichier ;
* statut ;
* date d’expiration.

Prévoir un nettoyage des uploads abandonnés uniquement si nécessaire.

INTERDICTION :

* faux paiement ;
* faux abonnement ;
* faux revenu ;
