INDAMORA PLAY — STAGING DE VALIDATION STRIPE SANS MODIFICATION DE LA PRODUCTION

OBJECTIF

Préparer un environnement de staging séparé et isolé permettant de lever les blocages actuels de validation Stripe, sans publier ni modifier la version LIVE actuelle du projet principal.

Le but est de pouvoir vérifier correctement :

* l’API INDAMORA PLAY ;
* /api/billing/plans ;
* le Checkout Premium ;
* Clerk et l’authentification ;
* le webhook Stripe ;
* la signature Stripe ;
* l’idempotence ;
* la mise à jour serveur du statut Premium ;
* les événements Stripe nécessaires ;
* la séparation TEST / LIVE ;
* les parcours mobile, desktop et application ;

avant toute décision de publication.

⸻

2. NE PAS PUBLIER LE PROJET PRINCIPAL

INTERDICTION DE PUBLIER LE PROJET PRINCIPAL EN LIVE pendant cette opération.

Ne pas utiliser la publication de production pour contourner les blocages.

Ne pas effectuer de publication partielle si Replit indique que les différents artifacts sont publiés ensemble.

Ne pas considérer une publication comme un moyen de test.

Si une vérification ne peut pas être effectuée sans publication du projet principal :

STOP.

Ne pas contourner cette règle.

3. CRÉER OU PRÉPARER UN STAGING ISOLÉ

Si l’environnement Replit le permet, préparer un environnement de staging séparé.

Le staging doit être clairement identifié comme :

INDAMORA PLAY — STAGING

Il doit être séparé de la production concernant :

* endpoints ;
* secrets ;
* Stripe ;
* webhooks ;
* données de test ;
* URLs de callback ;
* configuration Clerk si nécessaire.

Ne jamais mélanger TEST et LIVE.

⸻

4. STRIPE : UTILISER STRIPE TEST POUR LE STAGING

Le staging doit utiliser en priorité Stripe TEST.

Ne pas effectuer de paiement réel.

Ne pas créer de véritable abonnement LIVE.

Ne pas effectuer de don réel.

Ne pas modifier les produits ou prix LIVE existants.

Les offres Premium canoniques déjà existantes doivent être réutilisées lorsque possible.

Offres à vérifier en TEST

* Afrique : 500 XAF / mois
* International : 5 EUR / mois

Vérifier leurs Price IDs TEST.

Vérifier explicitement :

* livemode=false
* devise ;
* montant ;
* récurrence mensuelle ;
* produit associé.

Ne pas supposer qu’un Price ID est TEST simplement parce qu’il provient de la configuration de développement.

⸻

5. SÉPARATION TEST / LIVE

Le problème actuel doit être diagnostiqué précisément.

Actuellement :

* /api/billing/plans en développement répond 200 mais ne confirme pas correctement les offres ;
* ReplitConnectors avec NODE_ENV=development a retourné des prix LIVE ;
* la cause de cette sélection n’est pas encore confirmée.

Identifier précisément pourquoi.

Vérifier notamment :

* variables réellement chargées ;
* environnement Stripe utilisé ;
* configuration Replit ;
* NODE_ENV ;
* clés Stripe ;
* Price IDs ;
* mode livemode ;
* ordre de priorité des variables ;
* éventuelles variables de production injectées dans le développement ;
* éventuels connecteurs Replit ;
* logique de sélection des prix.

Ne jamais résoudre ce problème en affichant ou copiant les secrets.

Dans le rapport final, afficher uniquement les noms des variables, jamais leurs valeurs.

⸻

Ne pas modifier les valeurs LIVE existantes.

Ne jamais afficher :

* clé secrète ;
* webhook secret ;
* token ;
* identifiant privé ;
* credential ;
* valeur complète d’une variable sensible.

8. CHECKOUT PREMIUM

Tester le vrai flux Stripe TEST.

Avec un utilisateur de test authentifié :

1. connexion via Clerk ;
2. accès à Premium ;
3. sélection de l’offre ;
4. création du Checkout Stripe TEST ;
5. redirection vers Stripe TEST ;
6. paiement avec un moyen de paiement de test ;
7. retour vers INDAMORA PLAY ;
8. réception de l’événement Stripe ;
9. traitement serveur ;
10. mise à jour du statut Premium ;
11. vérification que le statut est réellement confirmé côté serveur.

Ne jamais simuler artificiellement :

* un abonnement ;
* un paiement ;
* un statut Premium ;
* un revenu.

Créer/configurer uniquement un webhook Stripe TEST destiné au staging.

Ne pas modifier le webhook LIVE actuel.

Ne pas remplacer le webhook LIVE de production pendant cette opération.

12. ROUTE WEBHOOK

La route staging doit :

* exister ;
* répondre ;
* recevoir POST ;
* lire le payload Stripe ;
* vérifier la signature Stripe ;
* utiliser le secret correspondant au webhook TEST ;
* refuser les signatures invalides ;
* traiter les événements nécessaires ;
* être idempotente ;
* ne pas traiter deux fois le même événement ;
* mettre à jour le statut Premium côté serveur.

Tester notamment :

* customer.subscription.created
* customer.subscription.updated
* customer.subscription.deleted
* invoice.paid
* invoice.payment_failed
* les événements Checkout nécessaires au fonctionnement existant.

Ne pas supprimer les événements existants sans justification.

⸻

13. SIGNATURE STRIPE

Tester réellement :

Cas valide

Un événement Stripe TEST signé correctement doit être accepté.

Cas invalide

Une requête sans signature ou avec une mauvaise signature doit être refusée.

Le test actuel :

POST /api/stripe/webhook

sans signature ne doit pas être considéré comme un test fonctionnel du webhook.

Il doit permettre de confirmer que la route existe et protège correctement son accès.

⸻

14. IDEMPOTENCE

Vérifier le mécanisme existant de déduplication par identifiant d’événement.

Tester :

1. réception d’un événement ;
2. traitement ;
3. envoi du même événement une deuxième fois ;
4. absence de double traitement ;
5. absence de double activation Premium ;
6. absence de double écriture incompatible.

Ne pas introduire un deuxième système de déduplication si le système actuel fonctionne déjà.

Compléter uniquement si nécessaire.

⸻

22. CONDITIONS D’ARRÊT

STOP IMMÉDIATEMENT si :

* Stripe TEST et LIVE sont mélangés ;
* un paiement réel risque d’être effectué ;
* une modification de production est nécessaire ;
* une modification du webhook LIVE est nécessaire ;
* une migration production est nécessaire ;
* un secret doit être affiché ;
* une fonctionnalité existante doit être réécrite ;
* le staging ne peut pas être suffisamment isolé ;
* un test critique n’est pas vérifiable ;
* l’environnement Replit impose une publication globale pour poursuivre.

Dans ces cas :

NE PAS PUBLIER.
