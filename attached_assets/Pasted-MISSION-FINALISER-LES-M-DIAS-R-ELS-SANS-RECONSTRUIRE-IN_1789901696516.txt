2. AJOUTER UNIQUEMENT LES FONCTIONS MANQUANTES

A. SUPPRESSION SÉCURISÉE DES MÉDIAS

Ajouter une véritable suppression des fichiers dans Object Storage.

Il faut :

* une route serveur sécurisée de suppression ;
* vérifier que l’utilisateur connecté est propriétaire du fichier OU administrateur ;
* empêcher un utilisateur de supprimer le fichier d’un autre utilisateur ;
* supprimer réellement l’objet dans Object Storage ;
* gérer correctement les erreurs ;
* ne jamais supprimer un fichier sans autorisation.

Ajouter l’interface nécessaire uniquement là où elle manque :

Artiste

Permettre à l’artiste de supprimer ses propres médias lorsque cela est autorisé.

ADMIN

Permettre à l’administrateur de supprimer un média si nécessaire.

Ne pas créer un nouveau système de fichiers.

Utiliser exclusivement le système Object Storage déjà présent.

⸻

3. AJOUTER L’UPLOAD RÉEL DES AVATARS

Les avatars doivent utiliser exactement le même système de stockage existant.

Parcours attendu :

Artiste
→ Profil
→ choisir une vraie image
→ upload
→ stockage Object Storage
→ sauvegarde de la référence dans la base de données
→ affichage réel du nouvel avatar.

La base PostgreSQL ne doit pas contenir le fichier lui-même.

Elle doit uniquement conserver les informations nécessaires pour retrouver le fichier.

Respecter les contrôles de type et de taille déjà utilisés pour les images.

Ne pas créer un deuxième stockage spécialement pour les avatars.

⸻

4. PRÉVISUALISATION ADMIN DES SOUMISSIONS

Lorsqu’un artiste soumet une œuvre, l’ADMIN doit pouvoir réellement prévisualiser les médias associés.

Pour une soumission en attente, afficher si disponibles :

* titre ;
* artiste ;
* catégorie ;
* pochette réelle ;
* audio réel avec lecteur ;
* vidéo réelle avec lecteur ;
* autres informations utiles.

Les fichiers privés d’une soumission en attente doivent rester accessibles uniquement aux personnes autorisées, notamment l’artiste concerné et l’ADMIN.

Ne pas rendre publiquement accessibles les fichiers simplement parce que l’ADMIN doit pouvoir les prévisualiser.

⸻

5. LECTURE DES VRAIS MÉDIAS

Vérifier que les lecteurs HTML5 utilisent réellement les fichiers Object Storage.

Audio

Le lecteur doit lire le vrai fichier envoyé par l’artiste.

Vidéo

Le lecteur doit lire le vrai fichier envoyé par l’artiste.

Ne pas utiliser de fichier de démonstration lorsque le média réel existe.

Ne pas inventer de média de remplacement.

Respecter les mécanismes de streaming/range déjà présents.

⸻

6. DURÉE DES MÉDIAS

NE JAMAIS mettre une durée fictive.

Si la durée peut être extraite du vrai fichier :

→ enregistrer la vraie durée.

Si elle ne peut pas être extraite :

→ laisser la durée absente ou explicitement inconnue.

Ne jamais écrire automatiquement une valeur comme 3:45, 180 secondes, etc. sans qu’elle provienne réellement du fichier.

⸻

7. NETTOYAGE DES FICHIERS ORPHELINS

Sécuriser le parcours de soumission.

Exemple :

1. L’artiste téléverse une pochette.
2. L’artiste téléverse un audio.
3. Une étape suivante échoue.
4. La soumission n’est finalement pas créée.

Dans ce cas, les fichiers nouvellement téléversés ne doivent pas rester inutilement dans Object Storage.

Mettre en place un nettoyage des objets créés pendant une soumission lorsque l’étape suivante échoue.

Attention :

* ne jamais supprimer un fichier déjà utilisé par une autre œuvre ;
* ne jamais supprimer un fichier appartenant à une autre soumission ;
* ne jamais supprimer un média publié par erreur lors d’un simple échec d’une nouvelle soumission ;
* supprimer uniquement les objets temporaires réellement liés à l’opération échouée.

⸻

8. LIMITES ET SÉCURITÉ

Conserver les protections existantes.

Les limites déjà identifiées sont :

* audio : 100 MB maximum ;
* vidéo : 500 MB maximum ;
* image : 10 MB maximum.

Ne pas augmenter ces limites sans raison technique.

Continuer à vérifier :

* type MIME ;
* taille ;
* existence du fichier ;
* propriétaire ;
* droits d’accès ;
* statut public/privé.

Tester également les tentatives d’accès non autorisées.

⸻

9. TEST RÉEL DE BOUT EN BOUT

Après les modifications, effectuer réellement le parcours complet.

TEST ARTISTE

1. Se connecter comme artiste.
2. Ouvrir son profil.
3. Envoyer un vrai avatar.
4. Vérifier que l’avatar est réellement stocké.
5. Créer une vraie soumission.
6. Envoyer une vraie pochette.
7. Envoyer un vrai fichier audio.
8. Si le flux vidéo existe, envoyer également une vraie vidéo.
9. Vérifier la vraie durée si elle est disponible.
10. Envoyer la soumission.

TEST ADMIN

11. Se connecter comme ADMIN.
12. Ouvrir les soumissions.
13. Voir la soumission créée.
14. Voir la vraie pochette.
15. Lire le vrai audio.
16. Lire la vraie vidéo si présente.
17. Vérifier que les fichiers restent protégés avant publication.
18. Approuver la soumission.

TEST PUBLIC

19. Vérifier que l’œuvre apparaît réellement dans le catalogue/RÉPERTOIRE.
20. Ouvrir l’œuvre.
21. Lire le vrai audio.
22. Lire la vraie vidéo si disponible.
23. Vérifier que la pochette réelle est affichée.
24. Vérifier que l’avatar réel de l’artiste est affiché lorsque prévu.

⸻

10. TEST DE SÉCURITÉ

Tester également :

* utilisateur A ne peut pas supprimer le média de l’utilisateur B ;
* utilisateur A ne peut pas accéder à un média privé de l’utilisateur B ;
* utilisateur non autorisé ne peut pas supprimer un média ;
* un fichier trop volumineux est refusé ;
* un type de fichier interdit est refusé ;
* une soumission échouée ne laisse pas inutilement des fichiers orphelins ;
* un fichier déjà publié/utilisé n’est pas supprimé par erreur.

⸻

11. RÉPERTOIRE

RÉPERTOIRE reste le centre de l’écosystème.

Ne pas modifier son fonctionnement actuel sauf si nécessaire pour afficher correctement :

* avatar réel ;
* pochette réelle ;
* œuvres réellement publiées ;
* lecture des vrais médias.

Ne pas refaire RÉPERTOIRE.

⸻

12. BASE DE DONNÉES

Les fichiers eux-mêmes doivent rester dans Object Storage.

PostgreSQL doit conserver uniquement les références/métadonnées nécessaires :

* chemin ou clé du fichier ;
* type ;
* taille ;
* durée si réellement connue ;
* propriétaire ;
* statut ;
* relations nécessaires.

Ne pas stocker les fichiers binaires dans PostgreSQL.

⸻
