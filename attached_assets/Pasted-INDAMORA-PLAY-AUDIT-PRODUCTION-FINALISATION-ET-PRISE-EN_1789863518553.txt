INDAMORA PLAY — AUDIT PRODUCTION, FINALISATION ET PRISE EN MAIN COMPLÈTE PAR L’ADMINISTRATEUR

0. CONSIGNE ABSOLUE

INDAMORA PLAY est déjà en production.

La version actuellement déployée est la référence fonctionnelle.

NE RECONSTRUIS PAS LE SITE.

NE RECOMMENCE PAS LE PROJET DE ZÉRO.

NE REMPLACE PAS les fonctionnalités qui fonctionnent déjà.

NE SUPPRIME RIEN sans nécessité technique absolue.

NE MODIFIE PAS inutilement le design, le logo, la navigation ou l’identité visuelle existante.

La priorité est :

PRODUCTION ACTUELLE → AUDIT → COMPARAISON AVEC LE CODE → IDENTIFICATION DES MANQUES → CORRECTIONS MINIMALES → TEST → VÉRIFICATION → RETEST

Le principe général est :

Minimum absolu de modifications.

Si une fonctionnalité fonctionne déjà correctement en production, TU LA LAISSES EN PLACE.

Si une fonctionnalité est partiellement fonctionnelle, TU LA FINALISES.

Si elle est cassée, TU LA RÉPARES.

Si elle n’existe pas mais est nécessaire au fonctionnement attendu, TU L’AJOUTES DE LA MANIÈRE LA PLUS SIMPLE POSSIBLE sans reconstruire l’application.

⸻

1. PRODUCTION = RÉFÉRENCE PRIORITAIRE

Avant toute modification :

1. Inspecter le projet actuellement déployé.
2. Inspecter le code existant.
3. Identifier les différences éventuelles entre la version production et le dépôt/code actuel.
4. Ne jamais considérer automatiquement que le dépôt représente exactement la dernière version fonctionnelle.
5. Ne pas remplacer une fonctionnalité production fonctionnelle par une ancienne implémentation du dépôt.

La logique doit être :

VERSION PRODUCTION ACTUELLE + CODE EXISTANT → COMPARAISON → CONSERVATION DE L’EXISTANT → CORRECTIONS MINIMALES

Ne fais aucune migration destructive.

⸻

2. OBJECTIF FINAL

Je veux désormais pouvoir piloter INDAMORA PLAY moi-même depuis l’interface ADMINISTRATEUR, sans devoir passer par Replit pour les opérations normales du site.

L’application doit donc rester une plateforme publique pour les visiteurs et artistes, mais disposer d’un espace d’administration privé permettant au propriétaire du site de :

* voir l’activité du site ;
* voir les visites ;
* voir les utilisateurs ;
* voir les artistes ;
* voir les œuvres ;
* voir les soumissions ;
* gérer/modérer les contenus ;
* suivre les abonnements ;
* suivre les dons ;
* consulter les flux financiers disponibles ;
* consulter les statistiques ;
* gérer les contenus nécessaires ;
* consulter les événements importants ;
* effectuer les opérations administratives prévues par l’application ;
* et, lorsque c’est techniquement prévu et sécurisé, modifier certains paramètres sans devoir intervenir dans le code.

Je ne veux pas devoir passer par Replit pour administrer le fonctionnement courant du site.

Replit doit rester l’environnement technique/de développement.

L’application doit devenir mon tableau de bord de pilotage quotidien.

⸻

3. ESPACE ADMINISTRATEUR — PRIVÉ ET INVISIBLE POUR LES AUTRES

Créer/finaliser une interface :

ADMINISTRATEUR

Cette interface ne doit être visible et accessible que par mon compte administrateur autorisé.

IMPORTANT :

Ce n’est PAS suffisant de cacher le bouton ADMINISTRATEUR.

La protection doit être faite :

* côté interface ;
* côté API ;
* côté serveur ;
* côté base de données lorsque nécessaire ;
* et sur toutes les routes administratives.

Un utilisateur normal ne doit pas pouvoir accéder à l’administration simplement en connaissant l’URL.

Exemple :

/admin

doit être inaccessible à un utilisateur non autorisé.

Le contrôle d’accès doit être effectué côté serveur avant de retourner les données sensibles.

4. COMPTE ADMINISTRATEUR

Utiliser le système d’authentification existant, notamment Clerk, au lieu de créer un deuxième système de connexion.

Le compte administrateur existant doit rester administrateur.

Ne crée pas une nouvelle authentification parallèle.

Ne demande pas à l’utilisateur de gérer deux comptes.

L’administrateur doit être identifié de manière fiable côté serveur.

Si le projet utilise déjà une adresse ou un mécanisme administrateur existant, le conserver.

Si une amélioration du rôle administrateur est nécessaire, utiliser de préférence un mécanisme sécurisé basé sur les rôles/métadonnées Clerk plutôt qu’une simple vérification frontend.

IMPORTANT :

L’adresse email seule ne doit jamais être considérée comme une protection suffisante si une solution de rôle sécurisée existe déjà dans l’architecture.

Toute évolution doit cependant rester minimale et ne pas casser le compte administrateur existant.

7. VISITES ET TRAFIC DU SITE

Je dois pouvoir voir les mouvements et les flux du site.

Mettre en place ou finaliser un système de statistiques interne raisonnable permettant de mesurer réellement :

* nombre de visites ;
* visiteurs ;
* pages consultées ;
* pages les plus visitées ;
* œuvres les plus consultées ;
* artistes les plus consultés ;
* recherches effectuées lorsque cela est techniquement possible ;
* provenance générale du trafic lorsque disponible ;
* appareils/mobile/desktop lorsque disponible ;
* pays ou zone géographique générale lorsque disponible et conforme aux règles applicables ;
* durée/session lorsque réellement mesurable ;
* évolution dans le temps.

Afficher au minimum des périodes :

* aujourd’hui ;
* 7 jours ;
* 30 jours ;
* période personnalisée si simple à mettre en place.

Afficher des graphiques seulement avec des données réelles.

Aucune donnée fictive.

afficher clairement 0 ou « aucune donnée disponible ».

Ne jamais générer de faux visiteurs pour remplir les graphiques.

8. RESPECT DE LA VIE PRIVÉE

Les statistiques doivent rester proportionnées.

Ne pas exposer les données privées des utilisateurs dans le dashboard.

Les statistiques doivent servir au pilotage du site, pas à surveiller individuellement les utilisateurs.

Si une fonctionnalité analytique nécessite une information personnelle, vérifier qu’elle est réellement nécessaire et respecter les obligations applicables.
