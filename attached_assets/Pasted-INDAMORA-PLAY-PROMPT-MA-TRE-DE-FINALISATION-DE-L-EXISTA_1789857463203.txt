INDAMORA PLAY — PROMPT MAÎTRE DE FINALISATION DE L’EXISTANT

⚠️ CONSIGNE ABSOLUE — NE PAS RECONSTRUIRE LE PROJET

Tu travailles sur le projet existant INDAMORA PLAY.

NE RECONSTRUIS PAS LE PROJET.

Le projet existe déjà, possède une architecture, une identité visuelle, des fonctionnalités, une base de données, une authentification, un stockage et une navigation.

Ton rôle est uniquement de :

* finaliser ce qui est incomplet ;
* corriger ce qui est réellement cassé ;
* sécuriser ce qui doit l’être ;
* connecter les services nécessaires ;
* améliorer les fonctionnalités existantes lorsque cela est indispensable ;
* tester chaque modification ;
* ne jamais remplacer inutilement une fonctionnalité déjà fonctionnelle.

RÈGLE PRINCIPALE

PRÉSERVER → AUDITER → COMPLÉTER → TESTER → VÉRIFIER → CORRIGER → RETESTER

Ne considère jamais une fonctionnalité comme terminée simplement parce que le code compile.

Elle doit fonctionner réellement dans l’application.

1. PROTECTION DE L’EXISTANT

Avant toute modification :

1. Inspecte l’intégralité de l’architecture existante.
2. Identifie les fonctionnalités déjà opérationnelles.
3. Identifie les fonctionnalités partielles.
4. Identifie les fonctionnalités réellement cassées.
5. Identifie les doublons éventuels.
6. Identifie les risques techniques.
7. Ne modifie pas une fonctionnalité simplement pour la réécrire.

INTERDICTIONS

Ne pas :

* reconstruire l’application ;
* recréer une nouvelle architecture ;
* changer inutilement le framework ;
* remplacer Clerk ;
* remplacer le stockage existant ;
* remplacer la base de données existante ;
* refaire toute l’interface ;
* supprimer des pages fonctionnelles ;
* créer de nouveaux menus sans nécessité ;
* créer de fausses données ;
* créer de faux comptes ;
* créer de faux paiements ;
* créer de faux abonnements ;
* simuler des revenus ;

* promettre une rémunération automatique des artistes ;
* modifier le logo existant ;
* modifier inutilement l’identité visuelle ;
* changer le domaine ;
* supprimer des données existantes.

Toute suppression doit être techniquement indispensable et clairement justifiée.

5. VÉRIFICATION EMAIL OBLIGATOIRE À L’INSCRIPTION

Lorsqu’une personne crée son premier compte sur INDAMORA PLAY, elle doit pouvoir recevoir un email de vérification contenant un lien sécurisé.

Flux attendu

INSCRIPTION
      ↓
COMPTE CRÉÉ
      ↓
EMAIL NON VÉRIFIÉ
      ↓
EMAIL DE VÉRIFICATION ENVOYÉ
      ↓
UTILISATEUR CLIQUE SUR LE LIEN
      ↓
EMAIL VÉRIFIÉ
      ↓
COMPTE ACTIVÉ
      ↓

Utiliser Clerk

Utiliser les mécanismes natifs de Clerk pour la vérification email.

Ne pas créer un deuxième système d’authentification.

Ne pas créer inutilement de tokens personnalisés si Clerk fournit déjà cette fonctionnalité.

Ne pas stocker inutilement des tokens de vérification personnalisés en base.

⸻

Après inscription

Afficher clairement un écran ou message indiquant :

« Vérifiez votre adresse email »

Expliquer que l’utilisateur doit consulter sa boîte email et cliquer sur le lien de vérification.

Prévoir également :

* possibilité de renvoyer l’email ;
* état “email vérifié” ;
* état “email non vérifié” ;
* gestion correcte du retour après clic ;
* fonctionnement sur mobile.

⸻

Sécurité

Un compte dont l’email n’est pas vérifié ne doit pas être considéré comme un compte pleinement vérifié.

Respecter la configuration de sécurité existante.

Ne pas contourner la vérification côté frontend.

La vérification doit être confirmée par Clerk côté serveur / système d’authentification.

⸻

Tests obligatoires

Tester réellement :

TEST 1

Nouvelle inscription avec une adresse email.

Résultat attendu :

* compte créé ;
* email de vérification envoyé.

TEST 2

Utilisateur qui ne clique pas sur le lien.

Résultat attendu :

* compte toujours non vérifié.

TEST 3

Renvoi de l’email.

Résultat attendu :

* nouvel email de vérification envoyé.

TEST 4

Clic sur le lien.

Résultat attendu :

* email vérifié ;
* compte correctement reconnu comme vérifié.

TEST 5

Connexion après vérification.

Résultat attendu :

* connexion normale.

TEST 6

Test mobile.

TEST 7

Test d’un lien expiré ou invalide si Clerk le gère.

6. STRIPE — PAIEMENTS ET ABONNEMENTS

Intégrer Stripe au projet existant sans modifier inutilement l’architecture.

Stripe doit servir pour :

* abonnements Premium ;
* paiements récurrents ;
* dons ponctuels.

Ne jamais simuler un paiement.

Ne jamais considérer un paiement comme réussi uniquement parce que le frontend affiche “succès”.

La confirmation doit provenir de Stripe côté serveur.

7. ABONNEMENT PREMIUM

L’offre actuelle doit être présentée ainsi :

AFRIQUE

500 FCFA / mois

HORS AFRIQUE

5 € / mois

Texte explicatif à intégrer :

Les abonnements permettent actuellement de contribuer au fonctionnement et au développement de la plateforme associative INDAMORA PLAY ainsi qu’à la promotion des artistes.

Ajouter également une note claire :

Lorsque les ressources de l’association le permettront, une partie pourra être consacrée à des actions de soutien ou de rémunération des artistes.

Ne pas présenter cette rémunération comme une garantie.

Ne pas promettre de revenu aux artistes.

8. STRIPE CHECKOUT — ABONNEMENTS

Utiliser Stripe Checkout et Stripe Billing pour les abonnements.

Créer ou réutiliser les produits/prix Stripe appropriés.

Prévoir deux prix récurrents :

PRICE AFRICA

* montant : 500 XOF
* périodicité : mensuelle

PRICE INTERNATIONAL

* montant : 5 EUR
* périodicité : mensuelle

Les montants ne doivent pas être écrits en dur dans le frontend comme source de vérité.

Utiliser des Price IDs Stripe configurés côté serveur.

Exemple de variables d’environnement :

STRIPE_SECRET_KEY
STRIPE_WEBHOOK_SECRET
STRIPE_PRICE_AFRICA_MONTHLY
STRIPE_PRICE_INTERNATIONAL_MONTHLY

Ne jamais exposer STRIPE_SECRET_KEY au navigateur.

9. STRIPE ET UTILISATEUR CLERK

Conserver Clerk comme système d’identité.

Lorsqu’un utilisateur connecté souscrit :

1. récupérer son identité depuis Clerk ;
2. rechercher son client Stripe existant ;
3. créer un Customer Stripe si nécessaire ;
4. associer correctement le Customer Stripe au compte utilisateur ;
5. lancer Stripe Checkout ;
6. enregistrer les identifiants nécessaires ;
7. attendre la confirmation Stripe côté serveur.

Éviter de créer plusieurs Customers Stripe pour la même personne.

⸻

10. WEBHOOK STRIPE — OBLIGATOIRE

Créer ou finaliser le webhook Stripe.

Le webhook doit :

* vérifier la signature Stripe ;
* être sécurisé ;
* être idempotent ;
* traiter correctement les événements ;
* ne pas faire confiance aux données envoyées directement par le navigateur.

Gérer notamment les événements pertinents liés à :

* création d’abonnement ;
* mise à jour d’abonnement ;
* annulation ;
* fin d’abonnement ;
* paiement réussi ;
* paiement échoué ;
* renouvellement ;
* changement de statut.

Le statut Premium dans INDAMORA PLAY doit être déterminé à partir des informations Stripe confirmées côté serveur.

⸻

11. IDÉMPOTENCE STRIPE

Un même webhook peut être reçu plusieurs fois.

Le système doit donc empêcher :

* création multiple d’abonnement local ;
* traitement multiple d’un paiement ;
* double attribution d’un statut Premium ;
* double écriture comptable ;
* double traitement d’un événement.

Stocker ou gérer les identifiants d’événements Stripe lorsque nécessaire.

⸻
