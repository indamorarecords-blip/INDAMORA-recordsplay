PHASE 1 — DIAGNOSTIC UNIQUEMENT

Avant toute modification, inspecte le projet en lecture seule.

Détermine précisément :

A. Dashboard ADMIN

* Quel composant affiche les statistiques ?
* Quelle source fournit le nombre « 7 utilisateurs inscrits » ?
* Quelle requête/API fournit ce nombre ?
* Le dashboard dispose-t-il déjà d’une liste détaillée des utilisateurs ?
* Existe-t-il déjà une page, route ou composant de type directory/users ?

B. API ADMIN

Inspecte les endpoints ADMIN existants.

En particulier, vérifie l’équivalent de :

GET /api/admin/directory

Détermine :

* ce que retourne réellement l’endpoint ;
* quelles données il récupère ;
* comment il récupère les utilisateurs ;
* si les données viennent de Clerk ;
* si elles viennent de la base ;
* comment les profils sont associés ;
* si requireAdmin est appliqué ;
* ce qui se passe sans session ;
* ce qui se passe avec un utilisateur normal ;
* ce qui se passe avec un ADMIN.

C. Authentification

Vérifie précisément la protection actuelle.

Le comportement attendu est :

Sans session :
401 ou refus équivalent.

Utilisateur normal :
accès refusé.

ADMIN :
accès aux données ADMIN autorisées.

Ne diminue surtout pas le niveau de sécurité actuel.

D. Frontend ADMIN

Vérifie si :

* l’API est appelée ;
* la réponse est correctement reçue ;
* les données sont correctement parsées ;
* les données sont simplement non affichées ;
* un composant existe mais n’est jamais rendu ;
* une route existe mais n’est pas reliée au dashboard ;
* une erreur frontend empêche l’affichage ;
* un problème de permissions ou de session empêche le chargement.

E. Données

Vérifie si les 7 utilisateurs déjà comptabilisés existent réellement dans la source de données utilisée par l’application.

Ne crée surtout aucune donnée pour effectuer ce test.
